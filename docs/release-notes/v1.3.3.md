Nice MC824H support for a Bus-T4 gate controller, on top of upstream `v1.2.2`.

**Verified on hardware:** Nice MC824H (two-leaf 24 V swing gate, Hyke kit), firmware
`CD08`, with a flashed BiDi-WiFi module and an OXIBD plug-in receiver. Other controllers
are untested; the MC824H work is opt-in and detected from `INF_PRD`.

## Fixed in this release

On an MC824H a command is answered about 50 ms later by a DEP status of `STA_ENDTIME`
(`0x06`, "manoeuvre ended by timeout") that describes the **previous** run, while the
movement that was just ordered is only reported 3-4 s later as `STA_OPENING` /
`STA_CLOSING`. The component took that first packet for the end of the movement, so the
cover published IDLE with a clamped position (5 % / 95 %) and asked for a status
confirmation in between: two state changes per order, and the reason automations around
this gate carry a `for:` debounce.

`BusT4Cover` now records when a command was sent and whether the movement it asked for has
been reported as started. `STA_ENDTIME` is ignored until then, with a 5 s guard so a
manoeuvre that never starts still falls back to the previous behaviour. `send_cmd()` is
overridden on the cover, so the YAML buttons, the lock and `control()` are all covered.

## Everything this fork adds since `v1.2.2`

| Tag | Change |
|---|---|
| `v1.2.3` | Per-motor and multi-byte parameter access: `send_info_request()` gained request arguments (the MC824H needs a motor index) and `send_config_write()` gained an offset, so the deceleration zones `0x24`/`0x25` and the forces can be written. `INF_MIN_CLS` (`0x13`) decoded as the close position, since this unit does not implement `INF_POS_MIN`. |
| `v1.2.4` | `%X` logging fix for the 32-bit OXI remote serial. |
| `v1.3.0` | New `sensor` platform: publish a control-unit parameter as a Home Assistant entity (`register`, `motor`, `byte`). |
| `v1.3.1` | `offset` and `length` on that sensor, so a value behind a prefix decodes as a big-endian integer. |
| `v1.3.2` | Per-motor replies are filtered by the motor index the reply reports, so two sensors on the same register stop alternating. |
| `v1.3.3` | The `STA_ENDTIME` fix above. |

## Install

```yaml
external_components:
  - source:
      type: git
      url: https://github.com/fastm3/esphome-BusT4
      ref: v1.3.3     # or: v1, which follows the latest compatible commit
    components: [bus_t4]
```

A complete, commented real-world configuration is in
[`example-mc824h.yaml`](https://github.com/fastm3/esphome-BusT4/blob/main/example-mc824h.yaml):
gate cover with learned timings, ten register sensors, the deceleration zones and the forces
per motor, and the pre-flash write helpers.

## Known limits

- Only MC824H hardware has been verified. The RBS400/Robus path is inherited from upstream
  and unchanged.
- Writing a parameter is not range-checked: the control unit may clamp or reject a value, so
  read it back after writing (the example does).
- `0x98` answers `ERR_UNSUPPORTED` (`0xFD`) on an MC824H, so the "slave mode" parameter that
  the RBS400 family exposes is not available here. `0x96` and `0x97` are still untested.
- The component's version is reported in `dump_config()`, so the boot log shows which tag is
  actually running.
