The receive parser could deadlock the bus for hours: the transmit path only runs while the
parser is in `WAIT_SYNC`, so a frame that stopped arriving mid-way blocked every poll and
every command - and since the control unit only talks when it is polled or when the gate
moves, nothing was left to resynchronise on.

Reported first by another fork on a Robus RBS600, with the mechanism spelled out from
`busTask()`; the same defect was in this fork. It is confirmed here by the device history: the
cover went from `closed` to `open` without ever reporting an `opening` transition, across a
window of about 10 h 30 during which the device stayed connected to Home Assistant the whole
time (no `unavailable` entry). The API and the WiFi were fine; the bus was deaf. Moving the
gate with a remote brought it back, which is what the remote's traffic completing the stuck
frame would do.

From Home Assistant the symptom is easy to misread: the device answers, entities are
available, but commands do nothing and the cover stops following the gate.

## Fixed

- **A frame that stalls is abandoned after 50 ms.** The largest frame is
  `SYNC + length + 60 payload + length` = 63 bytes, i.e. 32.8 ms at 19200 8N1, and a frame
  arrives without gaps; a 50 ms gap can therefore only mean the frame will never complete.
  The parser returns to `WAIT_SYNC` and the transmit gate reopens, so the link recovers by
  itself instead of waiting for someone to move the gate.
- **A frame that fails a checksum no longer resynchronises in the middle of itself.** That is
  the most likely way into the stuck state: the remaining bytes of the frame still arriving
  are parsed as a new one, a payload `0x55` is taken for a sync byte, the byte after it for a
  length (any value 1..60 is accepted), and the parser then waits for bytes that never come.
  Such a frame now enters a `DISCARD` state that leaves on the next break - or on the same
  50 ms deadline, so it recovers even on a bus that never goes quiet.
- **Frames that cannot be queued are no longer lost silently.** Every send path called
  `write(&packet, 0)` and ignored the result, so a full transmit queue (32 frames) swallowed
  commands with nothing in the log. It is now counted and logged with target and command.

## New counters

Four getters are available for YAML, so the link can be watched instead of guessed:

| Getter | Meaning |
|---|---|
| `get_rx_discarded()` | frames the parser had to abandon |
| `get_tx_dropped()` | frames lost because the transmit queue was full |
| `get_tx_frames()` | frames actually sent |
| `get_rx_packets()` | valid frames received and dispatched |

`example.yaml` exposes three of them as diagnostic template sensors:

```yaml
sensor:
  - platform: template
    name: "Bus frames discarded"
    entity_category: diagnostic
    update_interval: 60s
    accuracy_decimals: 0
    lambda: 'return id(bus).get_rx_discarded();'

  - platform: template
    name: "Bus frames dropped (TX queue full)"
    entity_category: diagnostic
    update_interval: 60s
    accuracy_decimals: 0
    lambda: 'return id(bus).get_tx_dropped();'
```

A `frames discarded` that keeps climbing, on a bus that also reports a healthy
`packets received`, is this defect being caught in the act. `bus_t4` logs each discard at
WARNING with the parser state, the expected size and the bytes it had collected, so the log
says whether it stalled in `DATA`, `TRAILING_SIZE` or after a checksum failure.

## Upgrade

Nothing to change in YAML: the fix is internal. Pinning `ref: v1.3.4` (or the moving `v1`) is
enough.
