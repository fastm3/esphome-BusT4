# Nice MC824H notes

Reverse-engineered and verified against a **Nice MC824H** (firmware `CD08`) driving a
two-leaf swing gate (Hyke kit), over Bus-T4 with this component.

`INF_PRD` reports `MC824H`, and the component now switches to MC824H mode
automatically (`Mode: MC824H` in the boot log).

## What is different on this control unit

1. **Per-motor arguments.** The control unit has two motors/encoders. Its position
   (`INF_CUR_POS`) and its per-motor configuration parameters are only answered when
   the request carries the motor index as an argument. Without it, `INF_CUR_POS`
   answered a constant `1` for the whole manoeuvre (so the cover position never
   moved), and `0x24`/`0x25` answered values that did not match the gate behaviour.
   The replies are `[requested motor index] [2-byte big-endian value]`.
2. **No `INF_POS_MIN`.** The fully closed position is reported through `INF_MIN_CLS`
   (`0x13`) instead.
3. **Parameters wider than one byte.** `0x24`/`0x25` answer 3 bytes, so they can only
   be written with `send_config_write()`. A 1-byte `send_config_set()` cannot express
   them, and writing only the first byte would target the wrong field.

## Behaviour of the deceleration zones (measured)

Measured on the unit above: position range 0-4088, full travel ~3996 pulses,
cruise ~220-235 pulses/s, deceleration speed set to its maximum 8 (slow phase
~68 pulses/s).

- The deceleration starts at `end_of_travel - zone`: with `0x24` = 800 the slowdown
  began at ~3196 pulses, with 350 at ~3646, with 200 at ~3822. The parameter therefore
  behaves exactly as "number of encoder pulses covered at the deceleration speed
  before the end of travel".
- One full opening, both zones at 800: **28.4 s** of travel, plus **~5.6 s** before the
  control unit reports "fully open".
- With both zones at 350: **24.3 s** of travel.
- **Reducing one motor's zone does not change the total duration**: the manoeuvre ends
  when the slower leaf arrives, so both motors' zones have to be changed together.
- The ~5.6 s between the leaf reaching its final position and the control unit
  reporting "fully open" looks like a fixed end-of-manoeuvre phase: it is not affected
  by the zones, which sets a floor on what zone tuning can win.

## Using it from YAML

```yaml
# single-byte parameters (speeds)
- lambda: 'id(gate).send_config_set(0x45, 8);'

# 3-byte parameter: motor index first, then the 2-byte big-endian value
- lambda: |-
    uint8_t v[3] = {0x01, 0x03, 0x20};   // motor 1, 800 pulses
    id(gate).send_config_write(0x24, v, 3);

# per-motor read: the motor index is passed as an argument
- lambda: |-
    const uint8_t args[1] = {1};
    id(gate).send_info_request(FOR_CU, (T4InfoCommand) 0x24, args, 1);
```

To get a value into Home Assistant instead of the log, use the `bus_t4` sensor platform.
For a parameter whose layout is not established, publish one byte at a time:

```yaml
sensor:
  # opening force: 0x4A answered 01.04 on the reference unit
  - platform: bus_t4
    cover_id: gate
    name: "Force opening (byte 1)"
    register: 0x4A
    byte: 1

  # closing force: 0x4B answered 08.00
  - platform: bus_t4
    cover_id: gate
    name: "Force closing (byte 0)"
    register: 0x4B
    byte: 0
```

Which byte carries the force is not established: `0x4A` looks like `[?] [force]` while
`0x4B` looks like `[force] [?]`. Add the same register twice with `byte: 0` and `byte: 1`
to see both, and check which one moves when the force is changed on the control unit.

A complete configuration using all of the above lives in
[`example-mc824h.yaml`](../example-mc824h.yaml).

## Caveats

- The `CFG_*` names in `t4_packet.h` are known to disagree with two independent
  reference implementations (upstream issue #34). Everything documented here was read
  or written by **raw address**, never through those named setters.
- Ranges and even the existence of parameters vary by controller model; the values
  above are what this MC824H accepts. Always read a parameter before writing it.
- Multi-byte writes carry no range check: the control unit may clamp or reject an
  out-of-range value, so verify every write by reading it back.
